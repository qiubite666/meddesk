## 0. 为什么有两组数据（先看这段）

会话 A 期间观察到 97 次 429，我最初归因为「同机其它任务抢占共享出口 IP 配额」。**该归因是错的**，已核实并撤回：

- `general-purpose-1` 只跑 `internal/model` 纯单元测试，零网络；
- `general-purpose-2` 只跑 `httptest` + `internal/fake` 内存仓储，请求不出进程；
- 两者汇报均确认未对生产发起任何请求。

真正原因是**限流器实现缺陷**：`internal/cache/noop.go` 的 `Incr` 每次都重设 `expireAt = now + ttl`，把定长窗口变成了滑动窗口——只要请求间隔小于窗口长度，计数只增不减，累计到第 61 次即 429，而每个 429 又刷新 TTL，形成**自锁**，只有完全静默满 3 秒才解锁。Redis 版 `incrLua` 是 `if cur == 1 then PEXPIRE`，两者语义不一致；生产 Redis 关闭走 noop，于是走的是错的那个。

这解释了会话 A 里所有反常现象，尤其是「1 req/s 探针前 55 秒全 200、第 56 秒起连续 6 秒 429」——不是有外部流量，而是计数一路累加到阈值后自锁，与速率无关。

该缺陷已在 `v0.3.54` 修复（含回归测试与回退验证），14:49:52 重新部署。**会话 B 在修复后运行，3377 次请求 0 次 429、0 次 5xx**，即本报告的权威数据。

会话 A 的时延数字与会话 B 几乎一致（P95 32 ms vs 31 ms），因为限流只影响「能不能发出去」，不影响「发出去之后多快回」，这也从侧面说明缺陷只作用于配额判定。

### 1.2 限流前提与发送节奏

`/ledger/*` 受应用层限流：`RPS=20`、`Burst=60` → `limitWindow()` 折算为**固定窗口 60 次 / 3 秒**，按 ClientIP 计数。`/auth/*` 另有 nginx `rate=10r/m burst=5` 的独立限制（每分钟 10 次），本轮除启动时一次 `POST /auth/refresh` 外**完全没有触碰 `/auth/*`**。

会话 B 采取的发送节奏（对应上一轮的教训）：

| 措施 | 参数 |
|---|---|
| 基础速率 | **5 req/s**（每 3 秒 15 次，占 60/3s 配额的 25%） |
| 抖动 | 每次等待 ×(0.7 ~ 1.3) 随机，避免所有请求对齐窗口边界 |
| 429 退避 | **2s → 4s → 8s**，退避期间**不发任何请求**（含探针） |
| 阶段隔离 | 每个阶段之间 `sleep 3.5s`，让窗口彻底过期 |
| 并发规模 | 按「单窗口 ≤60 次」设计：**10 并发 × 5 条 = 50 次/批**，4 批凑满 200 条，批间 `sleep 3.5s` |
| 429 统计口径 | 只统计正式测量阶段；启动清场（清理历史残留）阶段的 429 单列 |
| 429 是否计失败 | 否。单独计数，退避重试成功后仍计入有效样本 |

实测结果：本轮 429 = 0，说明 5 req/s + 抖动 + 严格退避在修复后的限流器下**零触碰配额**。

## 4. 结论与风险

### 4.1 并发 merge 的失败计数会误导用户（唯一代码缺陷，已两次复现）

同一现象在会话 A（有 429 干扰）和会话 B（0 次 429）**都出现**，可排除限流因素：

| 会话 | base → after | imported | skipped | **failed** | 实际增量 |
|---|---|---|---|---|---|
| A（v0.3.53） | 2301 → 2401 | 86 / 1 / 13 | 3 / 73 / 76 | **11 / 26 / 11 = 48** | +100 ✅ |
| B（v0.3.54） | 2301 → 2401 | 94 / 6 / 0 | 0 / 65 / 70 | **6 / 29 / 30 = 65** | +100 ✅ |

- `errors[]` 内容为 `写入账单失败（34eb279b-…）` 这类文案；
- **最终数据完全正确**：总数精确 +100，无重复 id、无丢失；
- 根因：merge 走「先按 id 查存在 → 不存在则插入」，并发时两个请求都判定不存在，随后一个插入成功、另一个撞主键，被归类为 `failed`（`internal/ledger/import.go` 合并分支）；
- 影响：① 用户看到「失败 65 条」会以为丢数据；② `errors[]` 把内部 UUID + 内部措辞直接抛给前端，属信息质量与轻度信息泄露问题。
- 建议：插入改 `ON CONFLICT (id) DO NOTHING`，冲突计 `skipped` 而非 `failed`；文案改用户可读并去掉裸 UUID。

### 4.2 并发 PATCH 是「最后写入胜出」，无乐观锁

10 个并发 PATCH 同一条记录，最终落库 `107.17`（10 个候选值之一），文本与分值自洽，**没有半个值或 0**——单行 UPDATE 是原子的，接口全部 200。

但服务端没有版本号/乐观锁，前 9 次修改静默丢失，界面不会提示冲突。对单人使用可接受；若将来做「家庭共享账本」多人同改一笔账，这是可感知的数据丢失。

### 4.3 限流器缺陷已修复，但暴露了测试基础设施的盲区

- `noop.Incr` 的滑动窗口自锁（会话 A 的 97 次 429）已修，本轮 3377 次请求 0 次 429 即为回归证据；
- 教训：**生产 Redis 关闭时走 noop，而 Redis 版与 noop 版语义不一致**，这类「降级路径与主路径不等价」的缺陷只在无 Redis 的生产环境暴露，单测若只覆盖 Redis 实现就会漏掉。建议对 `cache.Cache` 的两个实现跑同一套契约测试（fixed-window 语义）。
- `/auth/*` 有独立的 10 次/分钟 nginx 限制，客户端若在令牌失效时循环刷新会立刻把自己锁死，需有退避。

### 4.4 查询没有明显瓶颈，但 `keyword` 在数据量变大后会最先退化

- 2100 条下所有查询 P95 在 26–51 ms，`keyword`（34 ms）与其他筛选（26–46 ms）**无可分辨差异**；
- 但 SQL 是 `lower(r.note) LIKE '%kw%' OR lower(r.category_name_snapshot) LIKE '%kw%'`（`internal/store/ledger_repo.go:441`），**前导通配符用不上 B-Tree**，只能靠 `user_id` 索引先过滤再全扫；
- 结论要精确：**「当前规模没有变慢的证据」，不是「证明不会慢」**。按此写法，10 万条量级 keyword 会明显脱离其他筛选。建议上 `pg_trgm` GIN 索引，或把关键词搜索限定在最近 N 个月。

### 4.5 内存

单进程内、3377 次请求、2400 条数据：RSS 28.3 → 29.3（查询后）→ **36.2（并发峰值）** → 28.9（清理后）。峰值 +7.9 MB，结束后仅比基线高 0.6 MB，**回落到位、无累积**。会话期间未重启（`NRestarts=0`、`ActiveEnterTimestamp` 未变），回落归因于 **Go GC**。

### 4.6 总体判断

| 维度 | 结论 |
|---|---|
| 响应时延 | 优秀。最差 P95 = 51 ms，仅为阈值（500 ms）的 1/10 |
| 并发时延 | 10 路突发 P95 98 ms，仍在阈值 1/3 以内，排队可解释 |
| 写入吞吐 | 受限于客户端 5 req/s 削峰，服务端无压力迹象（P95 31 ms 不随并发上升） |
| 批量导入 | 线性、快（1000 条 1.7 s），优于阈值 17 倍 |
| 并发一致性 | 条数与金额在并发写后完全自洽；报销标记幂等 |
| 缺陷 | 并发 merge 的失败计数与文案（4.1） |
| 风险 | PATCH 无乐观锁（4.2）、keyword 无索引（4.4）、`/auth` 10r/m 客户端需退避（4.3） |

## 附：复现方式

```bash
cd D:/workbuddy/工作台/meddesk

node --check tmp/perf-ledger.js          # 语法检查

# 完整三组：5 req/s + ±30% 抖动，阶段间隔 3.5s 排空窗口，结束自动清理
node tmp/perf-ledger.js --rps=5 --burst=15

node tmp/perf-ledger.js --smoke          # 小规模冒烟（约 40 秒）
node tmp/perf-ledger.js --mem-only       # 内存专项（同进程密集采样 RSS）
node tmp/perf-ledger.js --clean-only     # 只清理历史 PERF-* 残留
```

脚本关键行为：
- 令牌桶 5 req/s（桶 15）+ **±30% 抖动**，避免窗口边界突发；
- 429 退避 **2s → 4s → 8s**，退避期间零请求；429 单独计数、不计失败；
- 并发用例按「单窗口 60 次」设计（10 并发 × 5 条 × 4 批，批间排空 3.5 s）；
- 401 自动刷新会话（refresh token 轮转，回写 `tmp/test-session.json`）；
- 阶段级 429/5xx 增量打点，可定位污染发生在哪一段；
- `finally` + `SIGINT`/`SIGTERM`/`uncaughtException` 三处兜底清理。
